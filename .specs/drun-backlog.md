# drun: backlog

Work agreed for later (`FW-nn` in `drun_specification.md`). Nothing here
is part of v1.

| ID | Item |
| :--- | :--- |
| FW-1 | Placement beyond the leader: per-runnable leases in the FSM, spreading runnables over nodes |
| FW-2 | `hashicorp/raft-wal` as the log store, after a benchmark against bbolt. *Done 2026-11-27*: the default for new nodes (`raft.log_store`; v0.5.0, experimental upstream); on this host 1.3–2× the commits and ~9× faster 1–4 MiB appends than bolt, 320 vs 1023 MiB after compaction; `make bench-logstore` compares the two |
| FW-3 | Export of Raft's own metrics (go-metrics) to Prometheus. *Done 2026-11-27*: a go-metrics sink renders hashicorp/raft's, raft-boltdb's and raft-wal's metrics on `/metrics` (`drun_raft_…`, samples as histograms in ms), installed only with `metrics.listen` (§10.3, T-15) |
| FW-4 | Encryption at rest of checkpoints and snapshots. *Decided 2026-11-27*: left to the filesystem under `data_dir` (LUKS, ZFS, fscrypt), documented in the Setup Guide; drun could wrap the log and snapshots but not the SQLite stores without SQLCipher (SEC-7, R-2) |
| FW-5 | A separate UID (and systemd sandbox) per runnable. *Skipped 2026-11-27* (R-3 stays accepted). Spike on systemd 255: polkit gets no unit name for `StartTransientUnit`, so letting the service user create transient units would let it start any unit as root; a shipped template `drun-runnable@.service` (`DynamicUser=yes`) does get `unit` and `verb`, so a rule can allow exactly its start and stop. The way to do it, if taken up: that template, a launcher (`drun runnable exec %i`) that receives the binary, environment and stdio over the node's socket, and a go-plugin `RunnerFunc` |
| FW-6 | *Done in v0.2.0 of the specification*: the SQL store (`drun-store.md`) |
| FW-7 | Signed runnable manifests, as in veho, for third-party runnables. *Done 2026-11-27*: `key` instead of `sha256`, manifests verified at start (`pkg/runnable/manifest`, `pkg/semver`), `tools/runnable-manifest`; the release signs the examples with drun's key (§8.8) |
| FW-8 | Non-voter promotion helpers (autopilot-like health checks). *Done 2026-11-27*: `member show` (health as the leader judges it), `member promote` and gated `member add` of a voter (healthy for `--stable`), `member demote` (FR-17); automatic promotion stays out |
| FW-S-1 | Leader-local interactive transactions shipped as SQLite changesets (session extension) |
| FW-S-2 | Group commit of concurrent batches into one Raft entry. *Dropped 2026-11-27*: hashicorp/raft's leader loop already writes every ready entry in one `StoreLogs` (one fsync); on the dev host, 3 nodes, raft-wal, 1 KiB: 108 commits/s with one writer, 520/s with 16; `BatchApplyCh` gave 290/s. The store does not fsync per batch (WAL, `synchronous=NORMAL`), the apply path does 19 000 batches/s (EXT-S-5), and grouping batches in one SQLite transaction would make page allocation, and so `store.max_size` (STO-8), depend on the grouping |
| FW-S-3 | Stale reads from followers for administrators and reporting. *Done 2026-11-27*: `store query --local` returns the index read at and the member's lag; `--max-staleness D` bounds it (STO-18) |
| FW-9 | Preferred-leader policy (e.g. the region closest to the runnable's external systems), by leadership transfer after an election. *Dropped 2026-11-27*: no automatic policy; an operator places leadership by hand with `leader transfer --to ID` (FR-3) |
| FW-10 | A fence helper in the SDK for runnables that also write to an external database (§8.5). *Done 2026-11-27*: `pkg/runnable/fence/postgres` on pgx (`Claim`, `Check`, `Tx`), keyed by cluster and runnable; the fenced-counter uses it; other databases stay the documented pattern |
| FW-11 | *Specified 2026-11-28 in `drun-stop.md`, for approval.* A node's graceful stop can hang (lab chaos run 20261128-033051, 1 of 26 graceful restarts): drun-b2, a follower that had lost leadership 24 s before, logged `stopping: handing leadership over` and never `stopped`; systemd killed it after `TimeoutStopSec` (90 s). The cluster kept serving (drun-a2 led throughout). In `Daemon.Stop` only `d.done.Wait()`, raft's `Shutdown` and `Store.Close` wait without the grace context. To do: dump the goroutines when the stop outlives its grace, then exit; reproduce with graceful restarts right after a lost leadership on the lab; fix the wait that hangs |
| FW-12 | Lab follow-ups from the first overnight runs. *Done 2026-11-28*: `lab.sh binary` documents building with the release's version (a `-SNAPSHOT` version is refused by the signed manifests); the fenced-counter `check` is skipped while a `pg-kill` fault holds PostgreSQL down; a graceful restart's stop (`restart-stop`) and recovery are timed apart |
